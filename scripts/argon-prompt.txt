Привет, Аргон! К тебе обращается Antigravity — ведущий инженер команды разработки проекта «На двоих» (Personal Digital Space for Couples в Telegram).

Мы провели глубокий аудит безопасности и архитектуры синхронизации проекта перед запуском в боевую эксплуатацию и хотим получить твой экспертный вердикт Senior/Staff уровня по ключевым узким местам.

НАШ ТЕКУЩИЙ СТЕК И АРХИТЕКТУРА:
1. Клиент: Чистый Vanilla JS (PWA/SPA), Telegram WebApp SDK, локальный стейт в localStorage, тактильный мобильный UI под iOS/Android.
2. Бэкенд: Node.js + Express + better-sqlite3 (WAL mode, embedded). Запущен в облаке Render.
3. Текущая синхронизация:
   - SSE-стрим (`/api/stream`) с таблицей `sync_log(coupleId, eventType, payload)` и поддержкой `Last-Event-ID`.
   - Прямой SSE-триггер `applyDelta` на клиенте для мгновенного добавления/обновления/удаления без ожидания полного pull.
   - REST-эндпоинты (`/api/wishes`, `/api/household`, `/api/pair`).
   - Версионирование сущностей: `{ version, hash, payload }`.
   - Первичное связывание пары с Auto-Merge.

ПРОБЛЕМНЫЕ ТОЧКИ, ВЫЯВЛЕННЫЕ НА АУДИТЕ:
1. Разрозненность данных: вишлист синхронизируется через sync-client.js, быт — через household-sync.js, а «Календарь дат» и «Главная цель» сейчас вообще живут локально в localStorage и не синхронизируются на сервер.
2. Офлайн-очередь (метро/лифт): клиентские dirtyIds и deleteIds живут в оперативной памяти (Set). При перезагрузке вкладки в офлайне удаленные записи могут воскреснуть.
3. Конфликты версий: если оба партнера одновременно отредактируют карточку, сейчас срабатывает защита с ручным диалогом выбора версии («онлайн» vs «локальная»), что ломает гладкий пользовательский опыт.
4. Безопасность: нужно перейти от передачи сырого initData на каждом запросе к сверхбыстрой защищенной сессионной модели (Session Token / JWT), строго исключающей спуфинг чужих Telegram ID (Zero Cross-Pair Leakage).

ВОПРОСЫ ДЛЯ АРГОНА:

1. Архитектура Real-Time транспорта для пары (Low Latency, Zero Server Overhead):
Является ли связка SSE (/api/stream) + REST-мутации оптимальной для мобильного Telegram Mini App (с учетом засыпания вкладки и переключений Wi-Fi <-> LTE), или легковесный WebSocket (ws) на Express даст меньший оверхед по памяти, лучшую устойчивость и более дешевый контроль онлайна партнера?

2. Модель бесконфликтного слияния (Unified Data Sync + No Conflict Popups):
Как спроектировать единый Sync Engine для всех 4-х сущностей пары (Планы, Быт, Календарь, Главная цель)? Какую модель слияния выбрать (LWW на уровне полей, CRDT/Yjs, или Operational Deltas), чтобы одновременные правки партнеров (например, один сменил дату, второй — комментарий) объединялись автоматически и бесшовно без показа раздражающих диалогов выбора версии?

3. Надежная транзакционная Outbox-очередь для офлайна:
Как грамотно реализовать клиентский Outbox Change Log (на базе IndexedDB / отказоустойчивого localStorage), который обеспечивает строгую FIFO-доставку мутаций с clientMutationId, подавление дубликатов, экспоненциальный retry и защиту от «воскрешения» удаленных записей после восстановления сети?

4. Защищенная сессионная авторизация в TMA:
Какой паттерн авторизации оптимален для Express + better-sqlite3: валидировать HMAC-SHA256 Telegram initData только при первичном входе и отдавать подписанный криптографический Session Token (JWT в HttpOnly Cookie / заголовок Authorization), или валидировать initData на каждый запрос? Как при этом надежно разделить Dev-окружение и Production без лазеек для подделки Telegram ID?
